# Changelog

## Unreleased

### Changed (breaking)

- Applicability is one condition with inheritance (cobotar/protocol#32): `variance.v1.VariantCondition` (`all_of`: one `AxisCondition` per axis, each with the options that satisfy it) replaces `VariantRule` and `VariantPredicate`, and `variant_rule.proto` is removed. `AssemblyNode.applicability`, `SequenceDefinition.applicability`, `TaskDefinition.applicability`, `TaskOverride.when` and `RecipeApplicability.include` are one condition instead of a list of rules, and `RecipeApplicability.exclude` is a list of conditions, any of which rejects the recipe. A node applies when its own condition and every ancestor's hold, and a sequence or task when its own, every ancestor sequence's and the recipe's include condition hold. An "or" across axes is expressed with a derived axis or with two nodes. A task override needs a non-empty condition, and the first override whose condition holds applies. Stored data: breaks for products, recipes and definitions with applicability; Authoring needs a reset.
- A recipe with applicability conditions needs `ProcessRecipe.product_definition_id`, and its conditions, and those of its sequences, tasks and task overrides, name axes and options of that product (cobotar/protocol#9). A checklist or startup procedure that needs conditions uses a placeholder product, or the machine itself as the product. Stored data: unaffected.
- Variant configurations in loads and recipe generation requests hold the selected axes only: the backend adds the derived axes, and refuses a configuration that misses a selected axis, names an unknown axis or option, selects a derived axis, is excluded, or for which a derived axis gets no option or several (`PROCESS_LOAD_FAILURE_INVALID_VARIANT_CONFIGURATION` for loads). `ProcessRun.variant_configuration` holds the full configuration, derived axes included. `VariantConfiguration` selects an axis only once, and `VariantSelection` requires key-shaped IDs. The recipe generation requests refuse `VARIANT_GENERATION_MODE_SELECTED_CONFIGURATION` without a configuration. Stored data: unaffected.
- `product.v1.ImportProduct.product` is optional: an import without a product creates or updates only its models and parts, e.g. an export of parts without their assembly (cobotar/Fusion360Exporter#19). `ImportProductResult.product` is set only when the import had a product. Stored data: unaffected.
- Models are created from uploaded files (cobotar/protocol#10, #31): `edit.model.add` takes `resources.v1.CreateModelArtifact` instead of a complete `ModelArtifact`. It names the uploaded files (`resources.v1.UploadedObject`) and holds only what a person or exporter knows; the backend fills in IDs, roles, file locations with size, digest and content type, and the content hash, and reuses a model with the same content hash. Uploads are content-addressed, at `<kind>/<sha256>/<filename>` (kind: `models`, `sidecars`, `thumbnails`), so an uploaded file is never overwritten. The file name in a key is limited to portable characters, has to end in an extension the request accepts, and can't be a name Windows reserves. Format, unit and axes: the format comes from the file extension when it isn't set, and the unit and both axes are required except for glTF and GLB files, which default to the glTF convention. Clients that create models (web-cobotar, the Fusion360Exporter) have to upload their files under such keys and send the new message. Stored data: unaffected.
- `common.v1.ExternalReference.system` and `external_id` are required, since imports match earlier imports by them (cobotar/protocol#31). Stored data: unaffected (Authoring stores no references yet).
- Updates of sequence and task definitions carry the recipe revision they were based on (cobotar/protocol#30): `edit.sequence_definition.update` and `edit.task_definition.update` take `process.v1.UpdateSequenceDefinition` and `UpdateTaskDefinition`, which hold the definition and `recipe_revision`, instead of the bare definition. The backend refuses an update if the recipe containing the definition has another revision, as it does for recipe updates. The tree requests (`AddRootSequenceRequest`, `AddChildSequenceRequest`, `RemoveSequenceRequest`, `AddChildTaskRequest`, `RemoveTaskRequest`) take an optional `recipe_revision` that is checked the same way. Stored data: unaffected.
- The Go module is `github.com/cobotar/protocol/v2`, since Go requires the module path of version 2 and later to end in the major version; v2.0.0 couldn't be used from Go. Go code imports `github.com/cobotar/protocol/v2/messages/...` and `github.com/cobotar/protocol/v2/subjects`. The npm, Python and NuGet packages don't change.
- Process recipes and part definitions have revisions (cobotar/protocol#19, step 2 of cobotar/protocol#17): `process.v1.ProcessRecipe.revision`, which covers the recipe's whole tree, and `product.v1.PartDefinition.revision`, both set by the backend and increased with every change. A revision is immutable, so clients may cache definitions by `(id, revision)`. Updates of recipes and part definitions have to carry the revision they were based on, and a stale one is refused; sequence and task definitions carry none of their own.
- `runtime.v1.ProcessRun.process_recipe_revision` and `part_definition_revisions` name the revisions a run was loaded with, and `ProcessRunDefinitions` holds definitions at those revisions.
- `common.v1.GetMessage.revision` gets a recipe or part definition at a revision, and a sequence or task definition at a revision of its recipe. The backend keeps the current revision and those runs use, for the retention period after their last run (or forever, if configured); a request for another revision fails.
- Stored data: Authoring stores revisions instead of per-run snapshots, and bumps its data version (cobotar/Authoring#53).

### Added

- Select-at-load variant groups (cobotar/protocol#35): `variance.v1.VariantGroup.select_at_load` marks a group the operator chooses every time a process is loaded, whatever named configuration is picked, e.g. the colour or material of an interchangeable part. Named configurations don't select its axes (and still select every other selected axis), and it can't have derived axes. `runtime.v1.ProcessLoadRequest.named_variant_choice` (`variance.v1.NamedVariantChoice`) is a third case of the `variant` oneof: a named configuration with the choices for the select-at-load groups (required, at least one selection), which the backend combines and checks like a `variant_configuration`. `named_variant_configuration_id` alone is refused for a product with select-at-load groups (`PROCESS_LOAD_FAILURE_INVALID_VARIANT_CONFIGURATION`). Existing products and loads are unchanged. Stored data: unaffected.
- A model of the whole product (cobotar/protocol#34): `product.v1.ProductDefinition.model_id`, e.g. the assembly exported from CAD, which clients show as the product's thumbnail and 3D preview; for a product with variants it shows one configuration. `ImportProduct.product_model_key` names one of the import's models as the product's model; without it, an import keeps the model of the product it updates. An imported product must not set `model_id` itself. Stored data: unaffected.
- `command.storage.collect_garbage` (`service.v1.StorageCollectGarbageRequest`, `StorageCollectGarbageResult`, `StorageObject`): removes the uploaded model files that no model refers to and no dump lists, older than `min_age` (one hour by default), or lists them in a dry run (cobotar/Authoring#17). Deleting a model leaves its files, since content-addressed files can be shared and dumps refer to them. Stored data: unaffected.
- Tool requirements met by the actor itself: `capability.v1.SkillDefinition.intrinsic_tool_roles` are the tool roles an actor with the skill fills without a tool, e.g. an operator's hands grip, position and align components. A task's `ToolRequirement` needs no tool for an actor whose skills cover its roles this way and that asks for nothing more (no `required_properties`, `minimum_capability` or `allowed_tool_definition_ids`); otherwise the actor needs a tool whose `ToolDefinition.actor_kind` fits it. `runtime.v1.TaskToolProvision` says how an actor meets the requirement, by itself (`by_actor`) or with the listed tool instances, in `CandidateActorEvaluation.tool` for each candidate and in `TaskRuntimeBinding.tool` for the assigned actor, so the AR runtime can show "by hand" or the tool to pick up. Stored data: unaffected.
- Derived axes and variant groups (cobotar/protocol#32): `variance.v1.VariantAxis.derivation` gives, for each option of a derived axis, the condition over selected axes under which it applies, so the operator is never asked for it (e.g. the main PCB, which follows from connectivity and memory). `product.v1.ProductDefinition.variant_groups` (`variance.v1.VariantGroup`) groups the axes that depend on each other; groups are independent, an axis outside every group is a group of its own, and within a group every combination is valid except the `excluded` ones, or only the `allowed` ones when given. A derived axis has to be in a group, and its conditions only name selected axes of that group. A product's conditions, allowed combinations and named configurations name only its axes and their options, allowed combinations and named configurations select every selected axis (of the group or the product), and an assembly node's applicability names axes of one group only. Stored data: unaffected.
- Named configurations (cobotar/protocol#32): `product.v1.ProductDefinition.configurations` (`variance.v1.NamedVariantConfiguration`), e.g. the rows of a configuration table. `runtime.v1.ProcessLoadRequest.named_variant_configuration_id` loads one instead of a `variant_configuration` (the two are a oneof), and `ProcessRun.named_variant_configuration_id` names the one a run was loaded with. Stored data: unaffected.
- `runtime.v1.ProcessLoadFailure.PROCESS_LOAD_FAILURE_INVALID_VARIANT_CONFIGURATION` and `ProcessRunIssue.variant_axis_id`, which names the axis an issue is about.
- `product.v1.ImportProduct` on the new route `edit.product.import` (active, served by Authoring, cobotar/Authoring#78): a product with its models (as `CreateModelArtifact`) and part definitions in one request, applied in one unit of work, answered with `product.v1.ImportProductResult` (the ID and CREATED, UPDATED or UNCHANGED status of the product and of each model and part, by key). Models and parts have keys within the request, by which parts name their default model and assembly nodes their part. Importing again updates the parts and product with the same external reference (a part gets a new revision) instead of creating new ones, while models are matched by content; two imported parts can't share a reference (cobotar/protocol#31). Stored data: unaffected.
- `runtime.v1.ProcessLoadRequest.done_task_definition_ids`: the tasks of the recipe that are already done, so a run starts after them, e.g. to restart a run that a backend restart aborted, or to start at a selected task (cobotar/protocol#28). Their task runs start DONE with `TaskRun.done_before_load`, and the runtime derives the other states from them. A task outside the recipe or the variant, a gap in an ORDERED sequence, or done tasks in two branches of an EXCLUSIVE sequence refuse the load with the new `PROCESS_LOAD_FAILURE_INVALID_DONE_TASKS`. Stored data: unaffected.
- The storage subjects (`command.storage.dump`, `command.storage.load`, `command.storage.clear` and `get.storage.info`) are active, now that Authoring serves them (cobotar/Authoring#62). The dump format is documented on `service.v1.StorageDumpRequest`, and `ServerInfo.reset_reason` lists the reasons, including `storage_loaded` and `storage_cleared` after a load or clear (cobotar/protocol#21).
- `resources.v1.StationDefinition.revision` and `CellDefinition.revision`, set by the backend and increased with every change. An update has to carry the revision it was based on, and Authoring refuses an update from an older revision instead of overwriting the changes made since (cobotar/Authoring#67). Clients that update stations or cells have to send back the revision they loaded.
- Free drive and robot plans as robot adapter capabilities (cobotar/protocol#24): `robot.v1.RobotAdapterCommandType` `FREE_DRIVE_START` and `FREE_DRIVE_STOP`; `robot.v1.RobotAdapterPlanType` (path, waypoints, joint angles) with `RobotAdapterPlanCapability` and `resources.v1.RobotAdapterDefinition.plans`; `resources.v1.ResourcePlanRequirement` as `ResourceRequirement.plan`, which only robot resource requirements may use; `common.v1.SignalSemantic.SIGNAL_SEMANTIC_ROBOT_FREE_DRIVE` for the output that puts the robot in free drive; and `robot.v1.RobotFreeDriveRequest` on the new route `command.robot_instance.free_drive.{robot_instance_id}`, which robot adapters serve.
- `ar.v1.ARResourceBindingStatus.AR_RESOURCE_BINDING_STATUS_OFFLINE`: the adapter of a bound resource isn't running, so every requirement on the slot is listed as unmet with the consumers that need it. Authoring reports it while it doesn't hear the adapter's heartbeats, without storing it (cobotar/Authoring#69).
- Subject catalog routes for every subject Authoring serves, publishes, requests or subscribes to: the run, task, availability and ownership commands, AR config input slots and presentation bindings, process recipe structure edits, field lookups, process recipe draft generation, `get.ar_config.info`, `get.process_run_definitions.one`, `get.backend.info`, the robot adapter's commands and requests, robot telemetry, task progress, device and server heartbeats, server restarts and log records (cobotar/Authoring#64).
- The adapter info subjects (cobotar/protocol#23): adapters announce their info on `report.robot_adapter.info.{robot_instance_id}` and `report.asset_adapter.info.{asset_instance_id}`, and Authoring reports changes as added, updated and removed events of the new `robot_adapter_info` and `asset_adapter_info` entities. The new `robot_adapter` and `asset_adapter` components stand for the adapters of robot instances (such as the UR adapter) and of asset instances, so the routes they serve, request and publish say so.
- `ARBindingCandidatesRequest` and `ARBindingCandidatesResponse`, plus `get.ar_config_binding.candidates`, for evaluating which resources satisfy an AR config slot without creating or changing a binding (cobotar/protocol#26).
- Entity-aware NATS route families, a generated `EntityName` API, and concrete CRUD/event subject contracts with per-entity protobuf metadata for Go, C#, TypeScript, and Python (cobotar/protocol#11).
- `ar.v1.FunctionType.FUNCTION_TYPE_ROBOT_ANCHOR` and `FUNCTION_TYPE_ROBOT_STATE`, which output a robot frame's anchor and the robot's state, replacing the anchor, state and colour properties that a robot input slot used to generate; and `ar.v1.FunctionAddMessage.robot_property_id`, so a robot function is linked to a slot when it is created, like feedback and actions (cobotar/Authoring#51).
- `common.v1.SignalSemantic.SIGNAL_SEMANTIC_ROBOT_ACKNOWLEDGE` for the robot input that an adapter pulses for the `ACKNOWLEDGE` command, so whether a connected robot can acknowledge shows in its signal catalog (cobotar/protocol#22).
- Resource capability requirements for feedback, action and function definitions; explicit AR input-slot constraints; and per-resource binding status with unmet requirements and affected consumers (cobotar/protocol#16).
- `resources.v1.AssetAdapterDefinition` and `resources.v1.AssetAdapterInfoMessage`, describing static asset commands, telemetry and standard signals separately from instance-specific identity and effective signals (cobotar/protocol#15).
- A shared `common.v1.SignalCatalog` for typed, readable and writable robot and asset signals, plus standard signal semantics for cameras, stack lights, conveyors, sensors, HMIs and part feeders (cobotar/protocol#15).
- `resources.v1.RobotAdapterDefinition`, describing the static commands, telemetry, supported robot types and configurable I/O register kinds supplied by an adapter implementation (cobotar/protocol#14).
- A staged, descriptor-validated NATS subject catalog and generated subject helpers for Go, C#, TypeScript, and Python. Planned routes remain available for incremental implementation without being treated as enforced runtime contracts (cobotar/protocol#11).
- `runtime.v1.ProcessRunDefinitions`: the recipe, sequence, task and part definitions a process run was loaded with, so every client shows and uses the same definitions as the backend while the run is active, whatever happens to the definitions afterwards. `source` says whether it holds the pinned definitions or, once the retention period after the run has passed, the latest ones. AR content isn't pinned and stays live. Published as an added event when a run is loaded (cobotar/protocol#18, part of cobotar/protocol#17).
- `runtime.v1.ProcessRunDefinitionsRequest` to fetch a run's definitions by process run ID.
- Predefined string rules and stricter field validation for execution evidence and evidence facts.

### Changed

- Generated Python modules import other protocol modules through the
  `cobotar_protocol` namespace instead of creating top-level packages such as
  `common`, `product` and `runtime` (cobotar/protocol#33). The Python package
  now declares its Protobuf and generated Protovalidate runtime dependencies
  and its actual Python 3.10 minimum.
- `plan.robot.path.{robot_instance_id}.{plan_id}` is published by robot adapters, not by Authoring.
- `edit.property_instance.update-value` is now `edit.property_instance.update_value`, since subject tokens are lower_snake_case.
- The reserved `edit.{entity}.reset.{child}` route is replaced by `edit.ar_config.reset.presentation_binding`, which takes an `ar.v1.PresentationBindingReset`.
- `get.ar_config_binding.candidates` and `get.asset_adapter.info` are active, since Authoring serves them.
- `resources.v1.ResourceSignalRequirement` now accepts an unspecified data type when `signal_id` or `signal_id_property_key` selects the concrete signal, allowing the selected signal to satisfy the requirement regardless of its type (cobotar/protocol#25).
- `resources.v1.AssetDefinition` now selects an asset adapter definition. `AssetDriverType`, `driver_type` and the robot-specific signal catalog messages have been removed; robot adapter info now uses the shared signal catalog (cobotar/protocol#15).
- `resources.v1.RobotDefinition` now selects a robot adapter definition, and `robot.v1.RobotAdapterInfoMessage` references that definition while reporting the connected controller identity, adapter version and configured I/O catalog. The former `RobotDriverType`, `driver_type`, legacy adapter identity fields and embedded `RobotAdapterCapabilities` have been removed (cobotar/protocol#14).
- `max_concurrent_processes` on lines, cells and stations is documented to count only active runs.

### Removed

- `resources.v1.RobotDefinition.model_id`; a robot's type now determines its 3D model. Field number 7 and the `model_id` name are reserved, while `coupler_model_id` remains available for the tool coupler model (cobotar/protocol#20).
